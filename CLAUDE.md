# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An in-progress "AI Internal Company Assistant": an orchestrator that routes employee requests to
specialized sub-agents (knowledge/RAG, performance/Atlassian, database/SQL, communication) and
fans results back in. See `Project Outline_ AI Internal Company Assistant.pdf` for the original
project brief.

**If `learnings.md` is present locally, read it before making architectural changes.** It is
the authoritative design log for this project — every non-obvious structural decision (why an
in-process graph instead of microservices, why hybrid routing instead of pure LLM or pure rules,
why `src/` layout) is recorded there with its rationale, not just its outcome, plus real bugs
found via live testing and how they were fixed. It also tracks, per component, what's
`Not Started` / `Designed` / `Implemented` / `Verified`. **It's kept out of version control
intentionally (personal design journal, not project documentation)** — if you're reading this
file from a fresh clone, it won't be there, and that's expected; this `CLAUDE.md` file covers
the essential architecture summary on its own. If you have local access to it and make a design
decision while working in this repo, update the corresponding section instead of leaving the
decision undocumented.

## Commands

Set up the environment (Python >= 3.11 required):

```bash
py -m venv .venv
.venv/Scripts/python.exe -m pip install -e ".[dev]"
```

`pyproject.toml` is the source of truth for dependencies; `requirements.txt` is a generated
mirror for tooling/CI that expects one (regenerate with `pip freeze` after changing deps, don't
hand-edit it).

Start Postgres + pgvector (required for the Knowledge Agent, Component 3):

```bash
docker compose up -d postgres
```

Copy `.env.example` to `.env` and fill in `OPENAI_API_KEY` before running anything that makes a
real LLM/embedding call — the Postgres vars in `.env.example` already match `docker-compose.yml`'s
defaults, so those don't need editing for local dev.

Performance Agent (Component 4) additionally needs a real Atlassian Cloud site (Jira +
Confluence) and Bitbucket workspace, with the remaining `.env.example` vars filled in
(`ATLASSIAN_*`, `BITBUCKET_*`) — account/sandbox setup is manual and personal-environment-
specific, not something this repo can script for you. Once credentials exist, the
`scripts/push_performance_fixtures_*.py` scripts seed the sandbox with synthetic data;
`scripts/chat.py` falls back to a "not seeded yet" message for Performance Agent if
`scripts/_performance_seed_state.json` (git-ignored, generated by the seeding scripts) isn't
present.

Run the full test suite:

```bash
.venv/Scripts/python.exe -m pytest
```

Run a single test file or test:

```bash
.venv/Scripts/python.exe -m pytest tests/unit/test_router.py
.venv/Scripts/python.exe -m pytest tests/unit/test_router.py::test_route_multi_agent_fan_out
```

Tests are async (`pytest-asyncio`, `asyncio_mode = "auto"` in `pyproject.toml`) — no
`@pytest.mark.asyncio` decorator is needed on `async def test_*` functions. All committed tests
use fakes (`FakeLLMClient`, `FakeAgent`, etc.) — no network calls, no API key required to run
`pytest`.

Live, real-API smoke tests are separate one-off scripts under `scripts/` (not part of `pytest`),
e.g. `scripts/smoke_test_llm.py` — these need `OPENAI_API_KEY` set and make real, billed calls.

No linter/formatter is configured yet.

## Architecture

**Ports and adapters.** Domain logic (`orchestrator/`, `agents/`) never imports a vendor SDK
directly. `core/llm_client.py` defines an `LLMClient` Protocol; `OpenAILLMClient` is the only
concrete adapter (this project has OpenAI API credits, never Anthropic ones — an
`AnthropicLLMClient` existed briefly and was removed since it would never be used). Same pattern
in `core/embedding_client.py` (`EmbeddingClient` / `OpenAIEmbeddingClient`) and
`integrations/vector_store/pgvector_store.py` (`VectorStore` / `PgVectorStore`). This is what
makes agent logic testable with fakes instead of live API calls — see `FakeLLMClient`,
`FakeEmbeddingClient`, `FakeVectorStore` in `tests/unit/`.

**Hybrid routing with a hard schema guardrail** (`orchestrator/router.py`,
`orchestrator/schemas.py`). The `Router` asks the LLM to reason about a request, but the LLM's
answer is forced through `RoutingDecision`, a Pydantic model whose `agents` field is a
`list[Literal["knowledge", "performance", "database", "communication"]]`, via OpenAI's Structured
Outputs (`OpenAILLMClient.get_structured_output`) — the model cannot return free text, only input
matching that JSON schema. If the response fails schema validation, `Router.route` retries
(`max_retries`, default 2) and raises `RoutingError` only after exhausting retries. A single
request can route to multiple agents at once (multi-intent requests fan out in parallel). The
same schema-guardrail mechanism is reused by the Knowledge Agent for generation, not just
routing — see below.

**Fan-out / fan-in** (`orchestrator/orchestrator.py`). `Orchestrator.handle()` calls
`Router.route()`, then runs every selected agent concurrently via `asyncio.gather` and returns an
`OrchestratorResult` keyed by agent name. Agents are looked up from a `dict[str, Agent]` passed
in at construction — the orchestrator has no knowledge of concrete agent implementations, only
the `Agent` Protocol (`core/agent.py`): `async def handle(user_request: str) -> AgentResult`
(`AgentResult` has an optional `metadata` dict for agent-specific extras like citations).

**Knowledge Agent (Component 3, implemented)** — `agents/knowledge/agent.py`. Real RAG: embed the
query (`OpenAIEmbeddingClient`) → retrieve from Postgres/pgvector (`PgVectorStore`, chunked via
`core/chunking.py`) → generate a schema-guarded answer (`KnowledgeAnswer`: `answer`, `citations`,
`answer_found`). Two mechanism details worth knowing before touching this code, both discovered
via live testing, both documented in detail in `learnings.md` Component 3's follow-up section:
- `retrieval_floor` (0.2, in `KnowledgeAgent.__init__`) is a cheap sanity check only — "is there
  any real signal at all" — **not** a per-chunk relevance filter. An earlier stricter per-chunk
  floor (0.5) silently dropped a genuinely correct retrieved chunk that scored 0.4791. Once
  anything clears the floor, every retrieved chunk goes to the LLM, and `answer_found` is the
  real groundedness gate.
- `chunk_document()`'s defaults (`chunk_size=400, chunk_overlap=60`) were picked empirically
  against this project's actual fixture docs, not guessed — see the chunking section of
  `learnings.md` #3 before changing them for a different corpus.

Scope note: Knowledge Agent only ever covers company-policy-style docs
(`tests/fixtures/knowledge_docs/` — PTO, expenses, onboarding, runbooks, FAQs). Confluence-sourced
sprint retro content lives in Performance Agent's scope instead (see below), not this one's.

**Performance Agent (Component 4, implemented)** — `agents/performance/agent.py`. Answers
questions about team delivery (sprint velocity, ticket activity, commit history) against a real
Jira/Confluence/Bitbucket sandbox seeded with synthetic data (4 fictional employees, 6 months,
13 two-week sprints). Architecturally different from Knowledge Agent's single-shot
retrieve-then-generate: this agent runs a genuine multi-turn **tool-calling loop**, since
performance questions are often exploratory (e.g. "compare velocity across the team" needs
several lookups, not one). This required a second method on `LLMClient` alongside
`get_structured_output` — `get_tool_response(messages, tools) -> ToolResponse`, using OpenAI's
native function-calling; the agent itself owns the multi-turn message history, keeping the
adapter thin.

Data access is direct REST API calls (`integrations/atlassian/{jira,confluence,bitbucket}_client.py`),
not MCP — genuine Atlassian Remote MCP Server access was investigated and built against
successfully at the protocol level, but real data calls are blocked by what looks like an EAP
(Early Access Program) gate on Atlassian's side, independent of any configuration on this
project's end. Direct REST stays the working path; MCP remains a documented future upgrade if
that access is ever granted. Two non-obvious auth facts worth knowing before touching these
clients: Jira/Confluence REST auth is Basic (email + classic API token), but Bitbucket's REST
API needs Basic auth with email too — while git-over-HTTPS (used only by the one-off seeding
script) needs the Bitbucket *username* instead. The two are genuinely inconsistent, confirmed
live, not a guess.

Two design choices worth knowing: (1) citations in `AgentResult.metadata` are collected
**programmatically** from actual tool-call results as they execute, not self-reported by the
LLM — more reliable, since there's nothing to ask the model to accurately report. (2) Tool
results that return lists include a pre-computed `count` field rather than leaving counting to
the model — confirmed live that the LLM can correctly fetch the right data and still miscount it
in prose (a well-known LLM weakness, not something a bigger model reliably fixes).

**Current implementation status:** Components 0/0.5/1/3/4 implemented and verified (unit tests
with fakes + live runs against real OpenAI/pgvector/Jira/Confluence/Bitbucket). Components 2,
5–11 not started — `database` and `communication` agents are still stubs that echo a canned
string. `scripts/chat.py` is a working interactive CLI entry point wired to the real orchestrator
(real Knowledge + Performance Agents, two remaining stubs) — `build_orchestrator()` in that file
is kept separate from the I/O loop so it can back a real API later without rewriting the wiring;
it supports a `/citations` command to toggle whether agent metadata (e.g. citations) prints
alongside answers, off by default. `evaluation/` and `api/` are still empty scaffolding — there
is currently no automated eval suite for retrieval/generation quality or agent *behavioral*
correctness (bugs like the ones above were only caught via manual live testing, not fakes) —
a real, acknowledged gap.

One maintenance note for whoever adds the next agent: `Router._SYSTEM_PROMPT`
(`orchestrator/router.py`) must keep each agent's domain description mutually exclusive. A real
bug shipped here once — Knowledge's description still mentioned "Confluence" from before
Performance Agent existed, and the router kept misrouting Confluence questions to Knowledge
(which has no real Confluence access) purely on keyword overlap between two agents' prompt
descriptions. If two agents could plausibly answer something adjacent, say explicitly in each
agent's description which one actually owns it.

## Package layout

Installable package lives under `src/enterprise_ai/` (`src/`-layout, declared in
`pyproject.toml` via `[tool.setuptools.packages.find] where = ["src"]`) — this is why the package
must be installed editable (`pip install -e .`) rather than run by adding `src/` to `PYTHONPATH`
manually.
